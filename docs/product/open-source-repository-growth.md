# Open-Source Repository Growth

## Purpose

Viable should help a public software repository become easier to discover, understand, evaluate, adopt, trust, contribute to, and support commercially.

The objective is not to manufacture stars or promise a position on GitHub Trending. GitHub does not publish a deterministic formula for becoming a top or trending repository. Viable can improve repository readiness, launch execution, community health, referral reach, and learning while clearly separating controllable work from platform outcomes.

## Growth funnel

```text
External impression
  -> repository visit
  -> README comprehension
  -> demo, install, or first successful use
  -> star, watch, or follow
  -> repeat use
  -> issue, discussion, or feedback
  -> contribution or dependency
  -> recommendation, sponsorship, or commercial lead
```

A repository is healthy when people progress through this funnel. Star count is one signal, not the product outcome.

## Repository marketability dimensions

| Dimension | Core question | Useful evidence |
|---|---|---|
| Problem clarity | Can a visitor understand the problem in seconds? | Repository description, README opening, demo |
| Product credibility | Does the project visibly work? | Releases, CI, tests, demo, screenshots, examples |
| Time to value | Can a qualified visitor reach success quickly? | Install steps, quick start, sample project, hosted demo |
| Discoverability | Can relevant GitHub and web audiences find it? | Topics, description, homepage, searchable terminology, referrals |
| Differentiation | Is the project clearly distinct from alternatives? | Comparison, architecture, use cases, tradeoffs |
| Trust | Is ownership, licensing, security, support, and maturity clear? | License, SECURITY, roadmap, status, maintainers, release history |
| Community readiness | Can people ask, contribute, and receive an answer? | CONTRIBUTING, code of conduct, templates, discussions, response time |
| Release discipline | Does the project create understandable reasons to return? | Versioned releases, notes, changelog, migration guidance |
| Distribution | Does each release reach the right communities? | Launch plan, newsletters, social, communities, events, integrations |
| Adoption | Are people using or depending on it? | Clones, downloads, dependents, packages, integrations, testimonials |
| Sustainability | Can maintainers support growth without collapsing? | Triage policy, automation, contributor path, funding, support model |
| Commercial path | Can qualified interest become a business conversation? | Website, documentation, contact path, enterprise or services offer |

## Viable repository assessment

A public repository workspace should capture:

- repository identity, owner, license, visibility, topics, description, and homepage;
- product category, audience, use cases, alternatives, and differentiation;
- README structure, first-screen clarity, demo quality, and installation path;
- community profile and health files;
- release cadence, release assets, notes, changelog, and upgrade path;
- CI, security posture, dependency health, issue hygiene, and response patterns;
- traffic, referrals, popular content, clones, stars, forks, watchers, discussions, contributors, release downloads, packages, and dependents where available;
- website, documentation, package registries, videos, articles, communities, and launch channels;
- adoption evidence and commercial calls to action.

Each finding must include evidence, confidence, impact, effort, owner, and verification method.

## Repository readiness checklist

### Product and proof

- The repository solves a real and specific problem.
- The implementation works beyond a screenshot or generated scaffold.
- The maturity level and known limitations are explicit.
- A short demo shows the product producing a meaningful result.
- Claims are supported by tests, examples, benchmarks, or reproducible evidence.

### Repository front door

- The repository name is memorable and searchable.
- The description states purpose, technology or category, and audience.
- The homepage points to the best product or documentation destination.
- Topics use relevant established terms and avoid vague tag stuffing.
- The social preview is legible and recognizable.
- The README explains the problem and outcome before architecture details.
- The first screen includes a clear value proposition, proof, and next action.
- Install and quick-start steps are copyable and tested on a clean environment.
- Screenshots, diagrams, and examples reflect the current release.

GitHub documents topics as a mechanism for finding related repositories and solutions, and permits up to 20 topics. Viable should recommend a smaller precise set based on audience language, category, technology, and use case rather than blindly filling every slot.

### Trust and community

- LICENSE states actual reuse rights.
- SECURITY explains private vulnerability reporting.
- CONTRIBUTING provides a realistic contribution path.
- CODE_OF_CONDUCT and SUPPORT define participation and help boundaries.
- Issue and pull-request templates collect actionable information.
- Good-first-issue and help-wanted work is genuinely approachable.
- Maintainer expectations and response targets are honest.
- Governance matches the project's actual size and maturity.

GitHub's community profile checks for recommended files including README, CODE_OF_CONDUCT, LICENSE, and CONTRIBUTING. Viable should surface that checklist but also assess whether the files are useful rather than merely present.

### Launch readiness

- The release has a focused story and audience.
- The release contains a working artifact, package, demo, or simple install path.
- Release notes explain benefits, changes, compatibility, and limitations.
- A coordinated asset package exists for GitHub, website, social, communities, newsletters, and relevant events.
- Maintainers are available for launch-day questions, bugs, and onboarding failures.
- Referral links and campaign identifiers are prepared where supported.
- The launch plan avoids unsolicited promotion and respects community rules.

### Ongoing growth

- Releases create meaningful reasons to return.
- Users are invited to share outcomes, not merely click Star.
- Issues and discussions are triaged consistently.
- Common onboarding failures become documentation or product fixes.
- Integrations and examples place the repository inside adjacent ecosystems.
- Maintainers contribute useful knowledge in communities before promoting.
- User stories, tutorials, benchmarks, and comparison material accumulate over time.
- Contributor recognition and release attribution are visible.

## Launch orchestration

Viable should create a repository launch plan with:

- primary audience and desired outcome;
- category and alternative framing;
- launch claim and supporting proof;
- release tag, notes, assets, and demo;
- README and documentation freeze checklist;
- social posts and community-specific variants;
- article, tutorial, video, newsletter, and event opportunities;
- maintainer coverage and response plan;
- measurement window and retrospective date.

The product should recommend a concentrated launch window only when the repository is ready to absorb attention. Sending thousands of visitors to a broken quick start is an unusually efficient way to convert publicity into distrust.

## Measurement model

### Discovery

- impressions from owned channels where available;
- repository views and unique visitors;
- referring sites and popular content;
- topic and search visibility observations;
- social preview click-through where measurable.

### Evaluation

- README depth and documentation visits;
- demo starts and completions;
- installation attempts and successful first runs where telemetry is consensual;
- package and release downloads;
- clone volume.

### Engagement

- stars, watches, forks, issues, discussions, and feedback;
- response time and resolution time;
- repeat visitors;
- newsletter or release subscriptions.

### Adoption

- active users where privacy-preserving measurement exists;
- packages and container pulls;
- dependents and integrations;
- cited use cases and testimonials;
- external tutorials and community references.

### Contribution and sustainability

- first-time and repeat contributors;
- accepted contributions;
- contributor onboarding completion;
- maintainer workload;
- support requests and issue quality;
- sponsorship, service, or commercial inquiries.

GitHub's repository traffic view provides clones, visitors from the prior 14 days, referring sites, and popular content. Viable should collect these measurements on a schedule because the native window is short.

## Trending and top-repository posture

Viable must not claim it can guarantee GitHub Trending or an undefined top-repository status.

Instead, it should:

1. define the desired audience and outcome;
2. benchmark comparable repositories by category and maturity;
3. improve all controllable readiness factors;
4. coordinate a legitimate concentration of useful attention around a meaningful release;
5. observe stars, forks, visits, clones, downloads, referrals, discussions, and adoption velocity;
6. compare the launch against prior baselines;
7. recommend product, documentation, release, and distribution changes;
8. record what was learned.

Any future trending-likelihood model must be labeled as an empirical estimate, show its source window and uncertainty, and avoid incentives for fake accounts, paid stars, reciprocal-star rings, or spam.

## Viable feature roadmap

### Repository workspace

- GitHub repository import and periodic refresh;
- repository and package metadata;
- README and community assessment;
- release and documentation inventory;
- public roadmap and issue health;
- adoption and traffic scorecard.

### Repository growth plan

- prioritized readiness recommendations;
- launch and release campaign builder;
- topic, description, social preview, README, demo, and quick-start guidance;
- community and contributor readiness plan;
- content and integration opportunity backlog;
- commercial conversion path review.

### Repository launch room

- release checklist;
- asset matrix;
- publication and community calendar;
- maintainer coverage;
- live traffic and engagement snapshot;
- issue and discussion triage queue;
- launch retrospective.

### Portfolio view

- compare public repositories across MythologIQ or another workspace;
- identify products worth promoting, consolidating, repositioning, or archiving;
- prevent multiple repositories from competing for the same category without clear differentiation;
- coordinate shared launch windows and cross-repository references without manufactured engagement.
