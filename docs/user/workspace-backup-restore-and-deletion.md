# Workspace backup, restore, reset, and deletion

Viable is local-first. A user-facing **workspace** therefore means the complete set of workspace-scoped local authority and workflow state, not only Product Core.

This guide documents the lifecycle implemented for issue #80.

## Product-wide workspace boundary

A Viable workspace is identified by one workspace ID shared across seven local contexts:

1. Product Core;
2. Campaigns and manual export records;
3. Signals;
4. Calendar and Learning;
5. Repository Growth;
6. Video Production;
7. Website Watch.

The Workspace screen inspects all seven contexts before backup, restore, reset, or deletion. A context can be **present**, **absent**, or **corrupt**. Absent optional downstream context is not fabricated merely to make a backup look complete.

The former Product-header reset control was misleading because it removed only Product Core and its active pointer while leaving downstream stores intact. The Product workflow now routes destructive workspace management to the dedicated Workspace surface instead.

## Backup

`Download workspace backup` produces one JSON file containing the seven workspace context slots. Each slot contains that context's local data or `null` when the context is absent.

Users do not author or paste JSON. The file is generated by Viable.

Before export, Viable verifies:

- Product Core exists and matches the workspace ID;
- each present context matches the same workspace ID;
- required arrays, records, and strings match the same minimum structural expectations used by the local stores;
- older compatible workspaces remain accepted when a later additive field is legitimately absent;
- no field name looks like a password, secret, API key, access token, refresh token, private key, or credential.

The backup includes a deterministic CRC32 checksum over canonicalized backup content. This detects accidental modification or truncation. It is **not** a cryptographic signature and must not be presented as proof that a backup came from a trusted party.

If any stored workspace context is corrupt or mismatched, ordinary backup is blocked rather than exporting a file that pretends to be restorable.

## Quarantine export

When a local context cannot be parsed or does not meet its minimum stored shape, the Workspace screen exposes `Export quarantine data`.

A quarantine file preserves the raw unreadable value, its local key, owning context, and the validation problem. Exporting quarantine data does not repair, rewrite, approve, or delete anything.

Because quarantine preserves raw local bytes as text, it may contain whatever the damaged local record contained. Treat the exported file as sensitive local data and store it accordingly.

Viable blocks destructive workspace deletion while corrupt context exists until quarantine has been exported during the current Workspace recovery session. This avoids turning a deletion button into the final destroyer of the only recoverable copy.

## Restore

Restore uses a file picker. Viable validates a chosen file before enabling a restore mutation.

Validation checks:

- backup format and version;
- workspace ID;
- creation timestamp;
- all seven context slots;
- per-context identity and minimum structural shape;
- credential-like fields;
- integrity checksum.

A failed validation changes no local workspace data.

### Restore into an empty profile

This mode is available only when the desktop profile contains no known Viable workspace data and no active workspace pointer.

Successful restore writes the contexts from the backup, restores the active workspace pointer, then re-inspects the restored workspace. If Product Core or any restored context fails integrity validation, Viable rolls the local state back and reports failure.

### Replace the current workspace

Replacement is allowed only when the profile contains the same workspace ID and no competing workspace ID. Viable will not silently combine or overwrite a different local workspace.

The existing values are snapshotted before writes. A partial-write failure triggers rollback to the prior local values and does not report success.

The replacement operation does not imply review, approval, publication, delivery, or measurement. It restores previously stored local state.

## Product-wide delete / predictable reset

`Delete or reset this workspace` is product-wide for the selected workspace ID.

Before confirmation, Viable shows:

- each of the seven contexts;
- whether it is present, absent, or corrupt;
- the number of counted local records;
- what remains outside workspace deletion;
- what is anonymized.

The user must explicitly review the scope and type `DELETE`. A final desktop confirmation follows.

Deletion removes:

- the Product Core workspace;
- Campaign state and export records;
- Signals state;
- Calendar and Learning state;
- Repository Growth state;
- Video Production state;
- Website Watch state;
- the active Product workspace pointer when it refers to the deleted workspace.

Deletion retains:

- Viable application files and code;
- backup or quarantine files the user already exported outside the app;
- unrelated operating-system, browser, or desktop-profile preferences that are not Viable workspace contexts;
- other explicitly distinct workspace IDs, if abnormal local state contains more than one. The Workspace screen shows those IDs separately rather than combining them.

Deletion anonymizes **nothing**. Workspace-scoped records are removed rather than copied into a hidden anonymous dataset or tombstone.

This policy intentionally means there is no retained in-app deletion record containing the deleted workspace ID. For a local-first workspace, retaining a hidden deletion tombstone after telling a user the workspace was removed would be a contradiction. Users who need a recoverable/auditable copy should export a backup before deletion, or a quarantine package when normal backup is blocked.

## Rollback behavior

Browser `localStorage` does not provide transactions. Viable therefore implements application-level rollback for restore and deletion:

1. snapshot every affected workspace key plus the active pointer;
2. perform the requested writes/removals;
3. verify the post-operation workspace condition;
4. restore the snapshot when a write/removal or integrity check fails;
5. report failure instead of reporting partial success.

Rollback is best-effort if the underlying storage itself is failing repeatedly. Viable never upgrades such a failure into a success claim.

## Retention

Viable does not currently run automatic retention pruning for these workspace stores. Data remains local until the user changes it through an owning workflow, restores a backup over the same workspace, or explicitly deletes/resets the workspace.

If automatic retention is added later, it must define its own preview, provenance, and recovery rules before it is allowed to remove authority or evidence.

## Demo and sample workspaces

Demo/sample data uses the same workspace boundary as ordinary data. There is no special partial reset that leaves dependent contexts behind.

To return a demo profile to a predictable blank state, use the Workspace screen's product-wide deletion. To recreate a known demo state, restore a validated backup into the resulting empty profile.

## Authority boundaries remain unchanged

Backup, restore, reset, and deletion are storage lifecycle operations. They do not:

- approve Product Core claims or ICPs;
- approve campaign content;
- schedule or publish content;
- claim provider delivery;
- create observed outcomes;
- convert a draft into reviewed authority;
- move authority from one workflow into another.

Draft, review, approval, selection, scheduling, export, delivery, provider verification, and observed outcome remain distinct states under their existing owners.
